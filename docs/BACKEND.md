# Backend implementation and operational limits

The API and worker use the same normalized relational schema in `db/001-initial.sql`, followed by numbered worker-monitoring, query-index, language, playback-block and title-redirect migrations. PostgreSQL is selected by a PostgreSQL `DATABASE_URL`; otherwise Node 24's SQLite database provides a persistent local installation. SQLite uses WAL, foreign keys, a busy timeout and serialized transactions. Production PostgreSQL uses pooled connections and transactional claims. The database handles durable jobs directly, rather than requiring a separate Redis deployment. Migration 1 is idempotently applied in an atomic transaction on connection; later migrations run once, and a PostgreSQL advisory transaction lock prevents concurrent web/worker startup DDL races.

## Start and administration

Run `npm run init`, then `npm run dev`; local development starts and supervises its background worker automatically. Production uses an independent worker with `npm run worker`. The initializer imports three actual Blender open-film identities through the same M3U pipeline used by administrators. The Sintel entry is explicitly a 52-second official trailer. Four sources initially have **unknown** health. They enter public discovery only after the worker checks actual media bytes or HLS manifests and sample segments. The delivered sample sources were checked successfully through the production outbound verifier on 4 October 2026; this does not guarantee perpetual availability.

The in-process command runner also works where spawning TypeScript compiler helpers is prohibited: `node scripts/run.cjs init`, `node scripts/run.cjs worker --once`, and `node scripts/run.cjs create-admin --email you@example.com --name Administrator`. Set `ADMIN_PASSWORD` to a 12–128 character password for account creation; it is never printed and no default administrator exists. Re-running administrator creation updates that account and revokes old sessions. Use the normal deployment environment for secrets; no administrator password is stored in configuration files by the application.

`SOURCE_ENCRYPTION_KEY` must be base64 for 32 cryptographically random bytes in production. Development creates `data/.source-key`. Preserve this key with encrypted database backups; losing or replacing it makes stored playlist snapshots and source URLs unreadable. `APP_ORIGIN` must contain the exact public origin in production; missing production configuration rejects mutations. In development without this setting, origin validation uses the actual HTTP Host header and Request.url protocol, allowing both localhost and 127.0.0.1 when each matches the browser's request host. This accounts for Next rewriting internal request URLs to localhost. Forwarded host/protocol headers never override that origin fallback. Cookies become Secure in production. Enable `TRUST_PROXY=true` only behind a reverse proxy that overwrites forwarded address headers. Without it, guest request rate buckets are shared, a deliberately conservative fallback.

## Availability and playback

New or changed source URLs are unknown and excluded. Successful container/manifest/sample checks mark an unblocked source healthy; one failed check makes it unavailable immediately. Public eligibility requires `health='healthy'`, `playback_blocked=0`, an enabled and present source, an enabled playlist when linked, and a published title. Degraded, unknown, unavailable and browser-blocked sources are excluded. One qualifying alternative keeps a movie visible. Series availability is computed separately for each episode. Failed playlist fetches preserve the previous imported source records; each source's independent health still controls visibility.

Movies and TV shows remain the default catalog, search and discovery scope. Live TV is available separately through `GET /api/catalog?type=live`, using the same strict source availability rule. Channel details, playback, retries and conversion accept published live titles with non-episode sources; linked playlists must be enabled. Live bookmarks and favorites work with registered lists and explicit guest collections, including title redirects. Live channels have no saved timestamp progress or watch history. Conversion starts live broadcasts at offset zero and returns an unknown duration.

Normal playback returns only healthy, unblocked sources, ordered by administrator priority, fewer recent failures and newer verification. Catalog and discovery use `no-store`; the player refreshes their results after failure or recovery. Source URLs are released only by playback and explicit retry endpoints; list, catalog, detail and administrator table APIs omit source URLs. A browser must necessarily receive a URL it plays. Provider API keys, password hashes, private playlist content and encryption keys are never included. Direct mode is only suitable for public URLs or provider-issued browser-safe URLs. Confidential long-lived upstream credentials must use the licensed signer integration; there is no unrestricted streaming proxy or access-control bypass.

A browser failure reported to `POST /api/playback/failure {sourceId,playbackAttemptToken}` immediately sets a persistent block and unavailable health on every source reference with the identical URL hash, records those failures, and queues a server check. Duplicate references across playlists, titles or languages therefore cannot keep the failed URL publicly available. Successful background checks cannot remove these blocks, including checks that were already running when the browser failed. Each reference needs its own fresh authorized browser attempt to recover; success for one reference does not restore the others. The blocks have no automatic expiry. Saving the same source URL, renaming it, or enabling it preserves the block. An actual URL-hash change resets verification and invalidates old reporting tokens; the replacement requires verification before normal discovery and inherits an existing block if that replacement URL is already blocked elsewhere.

`GET /api/playback/:titleId?episodeId=` returns opaque 15-minute `playbackAttemptToken` and `playbackAttemptExpiresAt` fields. They bind the source ID, original URL hash, request identity and latest block revision. `POST /api/playback/attempt {sourceId,playbackAttemptToken?}` issues a fresh authorized attempt for an explicit retry or token renewal. A blocked retry is marked `playbackRetry:true` and retains unavailable health until it succeeds; issuing or renewing the token alone never republishes it. A supplied expired token can authorize renewal while retaining its URL binding, but success and failure reports require an unexpired token. Obsolete URL reports fail with409; invalid/expired reporting tokens fail with403. Signing grants are rechecked against current source state before release.

The player sends `POST /api/playback/success {sourceId,playbackAttemptToken}` only after a playing event followed by forward playback advancement, excluding paused playback and seeks. The server requires a fresh token for the latest block revision, so a success from before a later failure cannot undo it. Accepted recovery clears the block, marks healthy and records browser success. This is browser-reported playback evidence; lightweight server probes do not certify codec support. Long-running playback renews reporting tokens without replacing the media URL already loaded by the player.

`PLAYBACK_SIGNER_URL` and `PLAYBACK_SIGNER_API_KEY` configure a real HTTPS signing adapter. Lume sends `POST {sourceId,url}` with bearer authentication server-to-server. The provider must return `{url,expiresAt}` where `expiresAt` is epoch milliseconds 15 seconds to one hour in the future. Returned URLs must use HTTPS, have no embedded credentials, and resolve exclusively to public addresses. Sensitive integration POST redirects are rejected. Per-source failures exclude that unsigned source while retaining successful grants in server rank order. Failed grants never fall back to private upstream URLs; if every grant fails, playback returns503. Invalid shared configuration blocks all grants. Logs include source IDs and sanitized errors, with source URLs redacted. `REQUIRE_PLAYBACK_SIGNER=true` disables direct mode unless a signer is configured. Signed URLs replace private source URLs before any browser response. Provider licensing, renewal policy and actual signer service credentials require deployment configuration and have not been tested against an external provider.

Health verification samples supported MP4/fMP4/WebM/MPEG-TS container bytes. WebM requires the declared EBML document type; Matroska and malformed EBML headers are rejected. HLS tries up to three master variants within a shared verification budget, checks initialization resources and first/latest media segments, and associates each segment with its own byte range, encryption key and IV. Supported AES-128 sample blocks are decrypted before validating media headers. The quality label derives from a verified HLS/DASH representation. Direct sources have no guessed quality labels. DASH supports ordinary BaseURL, SegmentList and SegmentTemplate addressing; complex nested addressing, encrypted/DRM manifests, unusual codecs and browser CORS cannot be certified by this lightweight server check. DRM entries require a configured licensed playback integration and stay unverified. The browser performs actual codec/CORS/playback checks and requests failover on errors. No entire feature film is downloaded by monitoring.

## Import matching and recovery

M3U supports quoted attributes, CRLF/BOM, `EXTINF`, `EXTGRP`, TV identifiers/logos/groups, release-year suffixes, spaced/separated SxxExx, NxN and Season/Episode identities. Explicit classifications take precedence; strong `/movie/`, `/series/` and `/live/` provider path hints also classify entries when groups are unfamiliar. Episode numbers are taken from display names rather than URL or TV-identifier digits. Malformed episode names remain in review. Quality suffixes are removed without stripping numeric movie names. Plain ambiguous entries are unpublished and queued for review.

Automatic merging requires matching known year and normalized content identity, a matching external identifier with consistent year/type, a matching series identity and episode coordinates, or unambiguous language-version evidence described below. Fuzzy similarity and ambiguous missing-year matches generate a review candidate rather than silently merging possible remakes. Multiple URLs remain separate sources. The administrator can merge titles, split one source, reassign sources and resolve review decisions. Merges migrate progress, watch history, favorites, lists, identifiers, aliases and episode links; metadata on the selected surviving title is retained.

Explicit language attributes (`audio-language`, `tvg-language`, `lang`, `language`), recognized wrapped/separated language tags, and edge flags populate per-source `language`. Ordinary title words are preserved, and missing/conflicting labels are not guessed. English, German and Turkish versions of the same work, for example, remain separate sources under one catalog title; switching language retains playback position and play/pause intent. Automatic failover stays within the selected language. Matching known-year versions share identity; missing-year language matches require unambiguous evidence, and conflicts with dated works or external identifiers remain in review. Language is included in stable entry identity so sources with different labels are retained.

For older imports, stop all workers and the development server that supervises them, then run `npm run repair-languages` once. The command uses encrypted saved snapshots to backfill language and original labels without fetching providers, removes explicit language wrappers from display names, and conservatively consolidates matching versions. It creates a consistent SQLite backup in a `backups/` directory beside the configured database and copies a local `.source-key` if present. Back up externally configured encryption keys separately. PostgreSQL needs an operator-created database/key backup before repair; the command does not create one. Restart workers after repair completes. The command does not invent availability or reset source playback blocks.

Merges keep old title IDs in `title_redirects`. Public details, playback, guest collections and registered progress/list writes resolve them to the surviving title, and existing redirects are retargeted during subsequent merges. Existing source IDs, user data and browser storage remain compatible. The Lume display name does not rename internal `luma` database paths, cookies or storage keys.

Synchronization compares stable entry identities, resets verification when URLs change, marks absent sources removed and preserves title/user data. Each successful changed playlist stores an encrypted snapshot and report. An administrator can queue restoration of a previous version with `POST /api/admin/playlists/:id/restore {versionId}`. An empty/invalid fetch or a shrink exceeding 80% for a playlist with at least ten entries preserves the previous catalog for review. Parsing errors suppress removals while permitting valid additions. Imported playlist snapshots are not publicly downloadable.

Imports parse the complete response before catalog mutations, then commit batches of 100 entries and yield between commits. Exact identities and bounded fuzzy buckets avoid scanning the entire catalog for each entry. Interrupted runs roll forward already committed batches; source removal and snapshot activation occur only after all entry batches finish. A persisted dirty state prevents an older unchanged snapshot from skipping reconciliation. Snapshot reports carry the parser version, so existing content is reprocessed after classification changes. Version repairs preserve source IDs and only automatically publish titles held solely for machine classification review without administrator locks; manual decisions and metadata conflicts remain protected.

A bounded starter set of never-checked sources from published titles receives earlier health-job timestamps, so a new playlist can establish initial availability before an older large queue drains. The selection spans content types and supported format hints, with at most three distinct titles per bucket and 36 checks per import. Remaining sources keep ordinary scheduling. Running jobs, attempted retries and previously checked sources retain their backoff. Starter checks use the same real media verifier and never publish unverified streams.

## Scheduling and security

Workers lease indexed queue heads transactionally, renew 120-second leases every 30 seconds, reclaim expired leases and retry errors with exponential backoff and jitter, up to four attempts. The default three consumers reserve one lane for imports while other lanes verify committed sources; one-consumer mode preserves ordinary FIFO processing. Each minute between import jobs a worker schedules due playlists and up to 1,000 due source checks. Health checks use bounded concurrency (default three, maximum eight), separate per-request deadlines, bounded bodies and exponential recheck intervals for failed sources. `HEALTH_INTERVAL_MS` defaults to six hours for healthy streams and has a five-minute minimum. Worker heartbeats update every 15 seconds, and administration reports offline after 60 seconds without a heartbeat. Run the worker continuously; web requests enqueue work and do not execute synchronization inline. SQLite releases its write transaction between import batches; PostgreSQL remains the deployment choice for large simultaneous imports.

Administrator-configured playlist/media requests permit HTTP(S) on any valid TCP port, with public, private, loopback, or internal hosts and optional embedded credentials. DNS answers are pinned to the connection and redirects are revalidated as HTTP(S); GET redirects may change scheme. All relative HLS/DASH resources use the same policy. Public-network SSRF blocking for these requests has been removed at the user's request: an administrator can reach services accessible to the web/worker host. Authenticated import bodies, downloaded playlist bytes, and parsed entry counts have no application cap; ordinary API bodies and health/media samples remain bounded. Large imports still consume browser/server memory and database capacity. Sensitive credentials are AES-256-GCM encrypted. Metadata bearer tokens remain in headers and are dropped on cross-origin redirects. Errors redact source URLs. Mutations require JSON and an exact same-origin header; database rate limits cover authentication, mutation, playback and failure reports. HttpOnly session tokens are stored only as SHA-256 hashes, passwords use salted scrypt, and API permissions enforce user/editor/admin roles independently of the UI. The optional playback signer separately enforces public HTTPS grants without embedded credentials.

## Metadata, search and account APIs

Automatic missing artwork/descriptions are enabled unless `METADATA_AUTO_ENRICH=false`. The no-key defaults use TVmaze for series, with Wikidata/Wikipedia as a fallback; films use confirmed Wikidata/Wikipedia identities. Lookups require unique title/year/type matches, include attribution, and use shared request limits and persistent cooldown/cache. The worker prioritizes verified movies and series and schedules bounded backfill rather than every imported entry. Results fill empty fields only and preserve administrator locks and identity changes.

`METADATA_LANGUAGE` defaults to `en` and accepts a two-letter language code with an optional region, such as `en-US`. `METADATA_USER_AGENT` supplies the descriptive application identity used for Wikimedia requests. Optional TMDB enrichment uses `TMDB_READ_ACCESS_TOKEN` in preference to `TMDB_API_KEY`. A licensed adapter takes precedence when both `METADATA_PROVIDER_URL` and `METADATA_API_KEY` are configured; otherwise TMDB is selected when its credentials are present, followed by the no-key providers when neither adapter is configured. Provider credentials remain server-side. The shared environment in `compose.yaml` forwards all seven metadata settings to web and worker. See [METADATA.md](METADATA.md) for provider contracts, image rights, configuration and the supported backfill command.

Exact/partial title, cast, director, genre and alternate-title searches query the complete catalog. Typo matching scores a bounded 1,000-candidate prefix/length window. Pagination and availability predicates apply before page selection. Large deployments should add PostgreSQL text/trigram indexing appropriate to their catalog and locale; the current index set covers identity, availability, schedules, history and job claims.

Optional accounts have separate persistent progress, history, favorites and watchlists. Guest progress stays in browser storage and reaches `/api/progress/migrate` only after explicit UI consent. Migration accepts at most 300 entries, validates title/episode identity and timestamp/duration bounds, and keeps newer account progress. `/api/library` returns up to 1,000 metadata records associated with the current account, retaining unavailable saved titles with an `available` flag. No email verification, password reset, social login, billing or subscription system is represented as implemented.

## Verification boundaries

`tests/backend.test.ts` exercises M3U identities and invalid input, media URL validation, authenticated encryption, direct/HLS/DASH sample failures, independent source availability, immediate failed-check hiding, series episode visibility, import replacement/removal/recovery, duplicate/remake safeguards, manual merge/split preservation, durable leases/retries, same-origin checks, account progress and an authenticated import-to-playback API workflow. Strict-availability tests cover sticky browser blocks, alternative servers, recovery/expiry/URL races, same-URL edits and old title IDs. Language and repair tests cover version grouping and saved-reference preservation. Upload tests cover imports above the previous size and entry limits. Outbound tests use real local HTTP servers on dynamically allocated ports. These tests use in-memory SQLite and injected or local upstream responses. PostgreSQL operations use the same SQL adapter but need a deployment integration run against a real PostgreSQL server. Server sample validation does not replace browser playback, codec, mobile accessibility, load or licensed-provider integration testing.
